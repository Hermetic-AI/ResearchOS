# ResearchOS 模块联动优化建议：从"功能孤岛"到"一张研究台"

> 视角：资深产品经理 / AI 架构产品。基于 2026-08-10 的代码库（dev）、`docs/researchos-product-design.md`（P1–P4）、`docs/chat-literature-integration.md`（L0–L3）、`docs/implementation-status.md`、`docs/optimization-checklist.md` 的现状盘点。只给方案，不改代码。

---

## 一、现状诊断：割裂感到底残留在哪

先说结论：**文献 × 对话这条联动主轴已经立起来了**（统一 rail、AgentDock 持久伴随会话、`@paper` 提及、相关会话互链、阅读笔记回流图谱，以及 `core/src/researchos-context.ts` 里已落地的 `researchos/library` + `researchos/selection` 两个 SystemContext 源）。用户感觉到的割裂，是**其余六个模块（Plot / Data / Reproduce / Translate / LaTeX / Graph）没有复制这条主轴**，具体拆成六层：

1. **实体层：paper 是唯一的跨模块实体。** dataset、notebook、chart、reproduce run、translation、手稿章节各自躺在各模块的 SQLite 里，没有统一身份、没有谱系（谁由谁产生、被谁引用）。`data` 的 `LinkExperimentInput` 记了 `tex_file/tex_section`、plot 有 `insert_to_paper`，但都是单向的、点对点的外键式记录，拼不成网。
2. **上下文层：Dock 的上下文注入只有文献有。** `agent-dock.tsx` 只在 literature 模块且选中论文时注入 `buildPaperSystem` + PDF 附件；在 data 页问"这个数据集该用什么检验方法"、在 plot 页问"这张图配色符合 IEEE 吗"，agent 并不知道用户眼前是什么数据集、什么 ChartSpec。
3. **事件层：模块间零广播。** schema 事件清单里没有任何 researchos 事件；reproduce 页靠 2 秒轮询取状态；复现跑完了、编译成功了、翻译归档了，其他模块和进行中的会话都不知道。
4. **索引层：会话与对象的绑定活在 localStorage 里。** `researchos.dockSession.<dir>:<module>:<resource>`、`researchos.paperSessions.<dir>.<paperId>`、`session-scope.ts` 的反查——换浏览器、清缓存即丢，多端不一致，也无法被服务端功能（如 orchestration）消费。
5. **图谱层：知识图谱只索引 `.md/.tex/.latex` 文件**，不索引研究产物。图谱实际是"文献关系图"，还不是"项目联结中枢"——查不到"这张图来自哪个 notebook、进了论文哪一节"。
6. **工作流层：Dashboard 的三条工作流（Discover / Experiment / Publish）目前只是文案**，没有真实的跨模块流转。用户要自己记住"复现完该去绘图、绘完该插论文"，每一步都要手工搬家。

一句话诊断：**产品现在是"七个模块 + 一个聊天"，而用户要的是"一个以研究对象为中心、对话随时在旁的工作台"。** 差距不在功能数量，在联结。

## 二、北极星与产品模型

**北极星一句话：每个研究产出都是一等"研究对象"（Research Object），对象之间自动结成图谱，对话是操作这些对象的统一界面。**

目标模型四件套（每件套都有现成地基，不需要另起炉灶）：

| 层 | 目标 | 已有地基 |
|---|---|---|
| 对象图谱 | paper / dataset / notebook / chart / run / translation / section / note / concept 统一登记、带谱系边 | literature.db 的 paper 实体、graph 的 SQLite 边表、`.researchos/` 存储约定、阅读笔记 sidecar 被 reindex 的成熟套路 |
| 焦点上下文 | 用户在哪个模块看哪个对象，会话每轮自动知道 | `researchos-context.ts` 双源（library/selection）+ Location 作用域节点 |
| 事件流 | 产物变更广播，会话与模块互相感知 | EventV2 管道、SystemContext 的 reconcile/update diff 机制 |
| Agent 编排 | 跨模块任务由 agent 规划执行，人只做检查点 | 7 MCP + 2 插件 + 8 SubAgent + 5 Command 的 preset 生态、Dock 三态（伴随/聚焦/后台） |

**三条判断，解释为什么走这条路：**

1. 文献轴的成功已经验证了模式：`焦点注入 + @提及 + 工具检索 + 笔记回流图谱` 四步闭环用户买账，把它泛化到全对象的边际成本很低。
2. opencode 底座给的三件套（Location 工作区、SystemContextRegistry、MCP/插件工具）就是为"领域上下文外挂"设计的，符合仓库"低侵入、不侵入内核"的架构原则。
3. 对标 Zotero/ima/Obsidian，ResearchOS 的差异化不是"又一个文献管理+聊天"，而是**可复现的研究谱系**：数据 → 分析 → 图 → 论文 → 复现，每一环可追溯。这是别的工具没有、而科研用户真正痛的点。

## 三、优化建议（A–F 六层 + 单点补强）

每条建议含：用户故事、现状缺口、方案、验收口径、优先级。

### A. 对象层：统一 Research Object 模型（联动的地基，最高优先）

**用户故事**：用户在 LaTeX 里看到 Figure 3，想知道这张图的数字是哪来的——点一下，跳回那张 chart，再点一层，是 notebook 的某个 cell，再一层，是数据集和那次复现 run。

**现状缺口**：各模块产物只有模块内身份，无全局 ID、无谱系边；graph 不索引产物。

**方案**：

1. 定义统一的对象引用格式，如 `ros:<type>:<id>`（type ∈ paper/dataset/notebook/chart/run/translation/section/note/concept），各模块 store 落一列 `object_ref` + `derived_from`（上游对象 ref 列表）。不建新库，各模块 SQLite 加列即可。
2. **Sidecar 索引**（复用阅读笔记的成熟套路）：每个产物落盘时顺手写一份元数据 md 到 `notes/artifacts/<type>-<id>.md`（含 wikilink 指向上游对象、cite key、产物路径）。graph reindex 现有管道天然把它们纳入图谱——零新索引代码。
3. 图谱边类型扩展：`derived_from`（数据→图）、`inserted_into`（图→章节）、`reproduces`（run→paper）、`translated_from`（译文→paper）。节点 drawer 加 "Open in ××" 深链。

**验收**：任选一次"复现→绘图→插入论文"链路，图谱画布能看到完整对象链；任意产物详情页展示上下游链接，点击可达。

**优先级**：P0（后面所有建议都依赖它）。

### B. 上下文层：把"文献焦点"泛化为"任意对象焦点"

**用户故事**：data 页选中一个数据集，Dock 里问"帮我选统计检验方法"，agent 直接知道数据集的列结构、样本量和已有的 cell 输出，而不是反问"你的数据长什么样"。

**现状缺口**：`researchos/selection` 源只表达 paperId；Dock 注入逻辑只写了 literature 分支。

**方案**：

1. `selection.json` 泛化为 `{ type, id, label }`（paper/dataset/chart/run/tex-section），`researchos-context.ts` 增加按 type 分发的 baseline 渲染：dataset 给列名+行数+最近统计，chart 给 ChartSpec 摘要，run 给当前步骤+关键指标，tex-section 给光标所在节标题。
2. 各模块页面在"选中对象变化"时调现有 selection 端点上报（literature 已有前端调用范式，照抄）。
3. Dock 上下文注入从"literature 特判"重构为"按模块类型取上下文包"：data → dataset schema + 最近 3 个 cell 结果摘要；plot → 当前 ChartSpec；latex → 当前文件+节；reproduce → run 状态快照。都走真实端点，取不到就退化为模块级摘要，**不伪造**。

**验收**：在 data/plot/latex/reproduce 四个页面各提一个依赖眼前对象的问题，agent 首轮回答即引用真实对象内容（可对照页面数据核验）。

**优先级**：P0。这是"对话与研究对象不割裂"在文献之外的直接复制，成本低、体感最强。

### C. 对话层：@提及泛化 + 会话-对象绑定搬到服务端

**用户故事**：用户在任何会话里输入 `@`，弹出论文、数据集、图表、复现任务四类候选；把一次关键讨论"钉"在某个对象上，三个月后从对象详情页还能找回来。

**现状缺口**：composer 只有 `@paper` 组；相关会话索引在 localStorage，清缓存即失。

**方案**：

1. `@` 自动补全按 `@paper` 的现有实现扩展出 `@dataset`（注入 schema + 前几行样本）、`@chart`（注入 ChartSpec + 缩略图路径）、`@run`（注入指标对比表）。全部解析为真实内容 part，沿用 file part 管道。
2. 会话-对象绑定落到服务端：给会话加轻量的 researchos 作用域记录（session 元数据或一张 `session_object` 关系表，走 protocol 组扩展），把 `paperSessions`/`dockSession`/`session-scope` 三处 localStorage 索引逐步迁移为服务端读写（前端可保留缓存做乐观显示）。这一步同时让"相关会话"在多端一致，并让未来的 agent 编排能查询"这个对象上发生过哪些会话"。

**验收**：换浏览器后论文详情页"相关会话"仍在；`@dataset` 提问能引用真实列名与样本值。

**优先级**：@提及 P1；绑定服务端化 P1（A 完成后自然要做）。

### D. 事件层：researchos 事件流 + 活动流面板

**用户故事**：复现 run 在后台跑完，Dock 主动冒一句"run #12 完成，指标与论文报告偏差 2.3%，要不要生成对比图？"——而不是用户自己回页面轮询刷新。

**现状缺口**：无 researchos 事件；reproduce 页 2s 轮询；长任务结果不通知。

**方案**：

1. schema 事件清单增补 researchos 事件（`artifact.created/updated`、`run.step_changed/finished`、`compile.finished`、`translate.finished`），挂进现有 EventV2 管道，前端订阅替代轮询。
2. Dashboard 增"活动流"（最近跨模块事件时间线）：它是用户感知"模块是活的、互相连着的"最便宜的界面。
3. 长任务收尾钩子 → Dock 建议（见 E 的 Next Best Action），把事件变成行动而不是通知噪音。

**验收**：reproduce 页不再轮询；一次 run 结束后 5 秒内，活动流与 Dock 都出现带行动按钮的条目。

**优先级**：P1（先只覆盖 reproduce/data/latex/translate 四个长任务源，别一次铺开）。

### E. 工作流层：三条"研究配方" + Next Best Action + 编排 Agent

**用户故事**：复现跑完，页面直接给"生成对比图"按钮 → 跳转 Plot Center 已预填指标数据与期刊主题 → 图满意后一键"插入论文 §Experiment" → LaTeX 页已就位 `\includegraphics` + caption。用户全程没有手工复制过一个路径。

**现状缺口**：跨模块跳转只有 literature → graph/translate/latex 几处；跳转不带数据预填；三条 Dashboard 工作流只是文案。

**方案**：

1. **Next Best Action（NBA）深链**：每个模块在自然收尾处给出下一步按钮，跳转带预填参数（全部复用现有 query 参数模式，如 `/graph?paper=<id>`）：
   - reproduce 对比视图 → "生成对比图"（预填指标表到 plot）；
   - plot 完成态 → "插入论文"（已有 `insert_to_paper`，补选章节的 UI）；
   - data artifact → "绘图"/"写入 LaTeX 表格"；
   - translate 归档 → "存为笔记并纳入图谱"/"对照原文阅读"（详情页入口）；
   - latex 编译成功 → "导出投稿包"/"检查引用格式"。
2. **三条配方做成 Command 预设**（不建工作流引擎）：`/reproduce-and-plot`、`/figure-to-paper`、`/read-and-map`（文献→翻译/笔记→图谱），每条就是编排好的 SubAgent 提示词 + 工具清单，装进 preset 由 Asset Center 一键启用。配方执行在聚焦态会话中进行，关键节点（跑实验、插入正文）停下等确认。
3. **research-orchestrator SubAgent**：preset 增一个总编排 agent，拥有全部 7 组 MCP 工具的视野与对象图谱查询能力，处理"帮我把这篇论文的方法复现并把结果写进手稿"这类跨模块请求；它的规划结果展示为可检查的步骤清单。

**验收**：三条配方各走一次端到端，产物谱系完整（A 的对象链可回溯）；任一 NBA 按钮跳转后目标页已预填真实数据。

**优先级**：NBA 深链 P1（便宜且立竿见影）；配方 Command P2；编排 agent P2–P3（先靠 NBA 人肉编排验证需求，再上自动编排）。

### F. 图谱层：从"文献关系图"升级为"项目联结中枢"

**用户故事**：用户问图谱"注意力优化相关的实验，哪些已经复现成功、图进了哪篇手稿"，RAG 返回带出处的回答：cite key + run 编号 + figure 编号。

**现状缺口**：graph 只索引 md/tex；RAG 语料不含产物；向量路径仍被强制降级。

**方案**：A 的 sidecar 落地后，图谱节点自然包含全部产物，此处做三件事：

1. 节点 drawer 按类型给模块深链（Open in Plot / LaTeX §X / Reproduce run）。
2. Graph RAG 的 seeds/subgraph 支持按节点类型过滤（只看产物链、只看文献簇）。
3. 向量路径按 L3 计划解锁（embedder 可用时去掉强制降级，不可用保持 FTS 明示）——这与 `chat-literature-integration.md` L3 一致，不重复设计。

**验收**：对一个真实项目问跨产物问题，回答含 cite key/run/figure 三类出处且可点击。

**优先级**：P2（依赖 A）。

### 单点补强（便宜但影响"整体感"）

1. **翻译回流**：文献详情页给"双语对照"入口（translation 归档已有路径约定）；翻译产出的术语表写成 concept 节点 sidecar，自动进图谱。现状翻译是"进去就出不来"的单向管道。
2. **LaTeX 溯源面板**：写作侧栏列出当前手稿的 figures/tables/citations 清单，每项带谱系徽章（来自哪个 notebook cell / run）。`LinkExperimentInput` 已存 `tex_file/tex_section`，反向展示即可。
3. **功能状态页 + 依赖健康页**（optimization-checklist P0/P3 未勾项）：割裂感有一部分来自"不知道哪些模块真能用"。一页讲清 可用/待配置/实验性，比十个模块各自报错体验好得多。
4. **完成 P4 收尾**：protocol 补 `citeKey`/`pdf_path`、preset install 覆盖 agents——这是既有计划的欠账，先于一切新特性。

## 四、优先级与路线图

**Wave 0 — 收尾欠账（先做，不加新特性）**

- [ ] P4：protocol 增补 `citeKey`/`pdf_path` 字段；install 端点落 agents（不只 mcp 块）
- [ ] optimization-checklist 未勾项：依赖健康状态页；LaTeX 引用插入+编译预览闭环
- [ ] 功能状态页（可用/待配置/实验性分级）

**Wave 1 — 焦点泛化 + 事件 MVP + NBA 深链（约 2–3 周，体感提升最大的一波）**

- [ ] B：selection 泛化 + 四模块 Dock 上下文注入
- [ ] D：事件流 MVP（仅 reproduce/data/latex/translate 四类长任务）+ Dashboard 活动流
- [ ] E1：五条 NBA 深链（预填参数跳转）
- [ ] 翻译回流的详情页入口

**Wave 2 — 对象模型 + 图谱纳新 + @泛化（联动的结构性工程）**

- [ ] A：对象 ref + derived_from 谱系 + sidecar 索引 + 图谱边类型
- [ ] C：`@dataset/@chart/@run` 提及；会话-对象绑定服务端化
- [ ] F：节点 drawer 深链 + RAG 类型过滤
- [ ] LaTeX 溯源面板

**Wave 3 — 编排与配方**

- [ ] E2：三条配方 Command 进 preset
- [ ] E3：research-orchestrator SubAgent（步骤清单式规划与确认）
- [ ] L3 向量路径解锁（embedder 就绪后）

**纪律**（沿用仓库既有验收文化）：一次一个纵切片；每个能力暴露真实状态与降级；不产生无出处的"证据"；每个 Wave 结束补端到端验收并在本文档打勾。

## 五、度量：怎么证明"不割裂了"

- **北极星：跨模块行动率** = 触发过 ≥2 个模块的会话占比（事件流落地后即可统计）。
- 辅助指标：带谱系的产物占比（有 derived_from 的 artifact / 全部 artifact）；NBA 按钮点击率；"相关会话"回访率；@提及中使用非 paper 类型的占比。
- 反向护栏：Dock 注入的上下文 token 预算（每模块上下文包设上限，按需 reconcile 注入，避免膨胀）；事件数/会话噪音比。

---

## 六、架构纪律与风险

1. **保持低侵入**：所有建议走 protocol 组扩展、SystemContext 注册、插件工具、preset 资产四条既有通道，不改 opencode 会话内核、不动 `src/generated`。
2. **不建三样东西**：不建工作流引擎（配方 = Command 提示词）；不建新存储（sidecar md + 现有 graph）；不建新导航体系（原生 rail 已统一）。
3. **localStorage 不再作为事实来源**：只做缓存与乐观显示；事实一律服务端/文件。
4. **风险与对策**：
   - 实体模型过度设计 → A 只加两列（ref、derived_from），语义靠 sidecar 文本表达，先跑通再抽象；
   - 事件流铺太开 → Wave 1 只接四类长任务源；
   - 上下文注入膨胀 token → 上下文包全部设字节上限，超限摘要化；
   - 编排 agent 越权执行 → 配方中"跑实验/写正文"节点强制人工确认（现有权限门控足够）。
