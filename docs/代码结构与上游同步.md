# ResearchOS 代码结构与上游同步方案

> 本文回答两个问题：ResearchOS 的代码放在哪里、怎么组织；以及这个 fork 如何长期、低痛苦地跟上 OpenCode 上游（`github.com/anomalyco/opencode`，默认分支 `dev`）的最新变更。

---

## 一、总体原则

1. **新增优先于修改**：ResearchOS 的代码 95% 以上落在新文件/新目录/新包里，对上游文件的修改压缩到一个尽量小的、可数清的清单内（见 §四"受控侵入点清单"）。
2. **依赖方向不可逆**：遵守 AGENTS.md 的依赖规则——Schema → Core/Protocol → Server；Client 永不依赖 Core/Server。ResearchOS 所有包处于这个方向的最下游。
3. **命名空间隔离**：自有包统一 `@researchos/*`，与上游 `@opencode-ai/*` 零碰撞；自有配置、Agent、Skill 统一放 `.opencode/researchos-*` 或以 `researchos-` 前缀命名。

---

在 bun workspaces 下新增以下包（root `package.json` 的 `workspaces` 已含 `packages/*`，无需改动）：

### 各能力的落地形态速查

| 能力 | 形态 | 位置 |
| --- | --- | --- |
| 文献/图谱/LaTeX/复现内核逻辑 | TS 库包 | `packages/researchos-*` |
| 数据分析、统计绘图（重 Python 依赖） | Python FastMCP server | `packages/researchos-mcp/*` |
| 轻量确定性工具（格式转换、Mermaid 校验） | plugin tool | `packages/researchos-writing`、`researchos-plot-core` 导出 plugin |
| 科研 SubAgent（文献/图谱/写作/数据/绘图/诊断） | markdown agent | `researchos-preset/agent/*.md` |
| 领域知识（论文阅读法、Graph RAG、润色规范） | SKILL.md | `researchos-preset/skill/*/` |
| 面向 Agent 的工具面 | MCP server 声明 | 用户项目 `opencode.json` 的 `mcp` 键 |
| 面向前端的持久化数据通道 | protocol group + server handler | 见 §四受控侵入点 |
| 前端页面 | SolidJS 页面 | `packages/app/src/pages/{literature,graph,latex,data,plot,reproduce}/` |

## 三、与 OpenCode 现有代码的结合方式

### 3.1 零侵入层（不需要 fork 也能工作）

这一层是 ResearchOS 的主体，利用 OpenCode 原生的扩展点：

- **MCP servers** — 用户课题项目的 `opencode.json` 声明：

```jsonc
{
  "mcp": {
    "researchos-literature": { "type": "local", "command": ["uv", "run", "--directory", "packages/researchos-mcp/literature", "researchos-literature-mcp"] },
    "researchos-data":       { "type": "local", "command": ["uv", "run", "--directory", "packages/researchos-mcp/data", "researchos-data-mcp"] },
    "researchos-plot":       { "type": "local", "command": ["uv", "run", "--directory", "packages/researchos-mcp/plot", "researchos-plot-mcp"] }
  },
  "plugin": ["@researchos/writing", "@researchos/plot-core"]
}
```

- **SubAgent / Skill / Command** — markdown 文件，由 OpenCode 的 config 目录机制自动发现（`.opencode/agent|skill|command/`）。`researchos-preset` 把这些打包，用户项目拷贝或通过全局 `~/.config/opencode/` 安装一份即可全项目可用。
- **Plugin tools** — `@researchos/writing` 等包默认导出 `Plugin`，经 `plugin: []` 数组注册，`tool` hook 注入自定义工具。

### 3.2 受控侵入层（必须改上游文件，但逐点可数）

只有以下 7 类修改点，每类都有明确的合并策略：

| # | 侵入点 | 修改内容 | 合并策略 |
| --- | --- | --- | --- |
| 1 | `packages/protocol/src/api.ts` | `makeApiFromGroup(...)` 追加 ResearchOS 的 group | 单行追加，冲突概率低 |
| 2 | `packages/protocol/src/groups/researchos-*.ts` | **新增文件**：literature/graph/latex/data/plot/reproduce 六个 group | 纯新增，零冲突 |
| 3 | `packages/server/src/handlers/researchos-*.ts` + `api.ts` | 新增 handler 文件 + 注册 | handler 纯新增；`api.ts` 单行追加 |
| 4 | `packages/app/src/app.tsx` | `Routes()` 内追加 ResearchOS 路由 | 集中在 `<Route>` 列表尾部追加；用标记注释包裹（见下） |
| 5 | `packages/app/src/pages/layout/sidebar-shell.tsx` | icon rail 追加模块入口图标 | 同上，标记注释包裹 |
| 6 | `packages/app/src/pages/session/composer/`（含 `prompt-input-v2.tsx`） | 资产快捷条组件挂载；`@` 提及扩展（@Skill/@文献/@数据集） | 挂载点用标记注释包裹；提及扩展优先以 provider 形式注册，避免改写原生逻辑 |
| 7 | `packages/desktop`（electron-builder 配置） | Tectonic 等二进制的 `extraResources` 分发 | 标记注释包裹，仅追加不改既有项 |

改完 1–3 后必须执行：`cd packages/client && bun run generate` 重新生成客户端 SDK（`src/generated*` 不可手改，CI 有 `check:generated` 守护）。

**标记注释约定**：所有对上游文件的修改，用成对注释包裹，方便合并时快速定位：

```tsx
{/* researchos:start */}
<Route path="/:dir/literature" component={LiteraturePage} />
<Route path="/:dir/graph" component={GraphPage} />
{/* researchos:end */}
```

### 3.3 禁止改动区

以下区域一行不改，保证上游同步与行为一致：

- `packages/core`、`packages/server` 的 Agent 调度、Session、权限内核（handler 新增除外）
- `packages/opencode` 的 tool registry、agent 运行时、MCP 运行时
- `packages/tui`、`packages/cli`（ResearchOS 首版不动 TUI）
- `packages/client/src/generated*`（只重新生成，不手改）
- `patches/` 下既有补丁（除非升级确需，见 §五）

## 四、数据通道：前端如何拿到科研数据

统一走 OpenCode 既有的 HttpApi 通道，不发明新机制：

```
app 页面 (SolidJS)
   │  @opencode-ai/client (生成的 SDK)
   ▼
protocol groups/researchos-*.ts   ← 契约定义（新增文件）
   ▼
server handlers/researchos-*.ts   ← 实现：import @researchos/* 包读写课题级 SQLite
   ▼
.researchos/*.db (课题目录)  ·  packages/researchos-mcp/* (Python 沙盒)
```

- 契约（protocol）只放 Schema 与 endpoint 定义，不放业务逻辑——保持 Client 可依赖 Protocol 的方向。
- 每个课题的科研数据存课题目录下 `.researchos/`（文献库 db、图谱 db、产物、venv），跟随课题走，天然多课题隔离。

## 五、上游同步策略（长期跟住 opencode/dev）

### 5.1 仓库与分支模型

```
upstream = github.com/anomalyco/opencode   (只读跟踪)
origin   = ResearchOS 自己的 fork

分支：
  dev            ← 长期主分支 = 上游 dev + ResearchOS 全部改动（默认分支）
  upstream-dev   ← 纯镜像分支，只 fast-forward 自 upstream/dev，永不直接提交
  <feature>      ← 短命特性分支（≤3 词、连字符，如 graph-rag-query），合入 dev
```

### 5.2 同步节奏与 Runbook

**节奏**：每两周同步一次；上游发 release tag 时额外同步一次。不要间隔超过一个月——冲突随时间指数增长。

**Runbook**（每次同步执行）：

```bash
git fetch upstream
git checkout upstream-dev && git merge --ff-only upstream/dev
git checkout dev
git merge upstream-dev          # 冲突预期集中在 §5.3 的热点清单
# 解冲突后：
bun install                      # 依赖可能变动，patches 会重打
cd packages/client && bun run generate   # 若 protocol 有变动
# 逐包验证（不可在根目录跑测试）：
cd packages/opencode && bun typecheck && bun test
cd packages/app && bun typecheck
cd packages/researchos-literature && bun typecheck && bun test
# ... 其余 researchos 包
```

### 5.3 冲突热点清单（按风险排序）

| 热点 | 原因 | 对策 |
| --- | --- | --- |
| `patches/` + root `package.json` 的 `patchedDependencies` | 上游升级依赖版本后补丁文件名/内容失效 | 同步后第一件事 `bun install` 验证补丁可打；失效补丁逐个人工 rebase；我们**不新增** patch |
| `bun.lock` | 双方都加依赖 | 接受上游版本后重跑 `bun install`，不手解 lockfile 冲突 |
| `packages/app/src/app.tsx` | 上游也在改路由/布局（v2 迁移进行中） | 我们的路由用 `researchos:start/end` 包裹，冲突时整段平移 |
| `packages/app/src/pages/layout*.tsx` / `sidebar-shell.tsx` | 上游新旧布局切换（`newLayoutDesigns`） | 关注上游 v2 布局落地，必要时把 rail 入口迁移到新布局组件；UI 集成方案见《UI集成方案.md》 |
| `packages/protocol/src/api.ts` | 上游新增 group | 单行追加，冲突时保留双方行 |
| `packages/ui` 主题令牌/组件 | v2 组件替换 v1 | 我们页面只消费令牌与公开组件，不 fork 组件源码；上游删 v1 组件时跟随迁移 |
| `packages/client` contract.ts | 上游改 endpoint 过滤 | 重新 generate 后 diff 检查 |

### 5.4 纪律（让同步成本不恶化）

- 任何 PR 若修改了非 `researchos-*` 的文件，必须在 PR 描述中列出修改点并说明为何无法以下游方式实现。
- 新增功能默认先问四个问题：能否做成 Skill？能否做成 SubAgent？能否做成 plugin tool / MCP server？能否做成新包？四个都不行才允许动上游文件。
- 每季度审计一次 `researchos:start/end` 标记数量——它应该保持不变或变少（上游机制变开放时把侵入点迁移到下游）。
- 上游若官方化了等价能力（如原生 skill 市场），ResearchOS 优先迁移到官方机制，删除自有实现。

## 六、验证与 CI 守护

- 同步后 CI 必跑：`bun run generate` 的 `check:generated`、各包 `bun typecheck`、各包测试。
- 为 7 个受控侵入点写一个轻量脚本 `script/researchos-sync-check.ts`：校验标记注释成对、ResearchOS group 已注册、路由存在——同步后跑一遍即可发现"静默丢失"的修改。
- 端到端冒烟：启动 server + app，依次打开 6 个 ResearchOS 页面并调用各一个 MCP 工具（可用 `packages/opencode` 的 e2e 设施）。

---

## 七、一句话总结

> **新增文件承载功能，标记注释圈住侵入，双周合并上游，patches 与 lockfile 先行验证**——做到这四点，ResearchOS 就能在 opencode 快速演进的同时保持可维护。
