# ResearchOS 前端深度优化方案

## 目标

把目前“多个能打开的模块页面”收敛为统一的科研工作台。优化顺序以真实任务完成率为准，而不是先追求视觉装饰：研究者应能一眼知道当前课题是否健康、下一步能做什么、某项能力为什么不可用，以及产物如何流向下一个模块。

## 一、先建立工作台系统，不逐页孤立重做

### 1. 统一壳层

所有 ResearchOS 路由使用同一个 `ResearchWorkspaceShell`，由四个稳定区域组成：

```text
模块导航 | 当前模块工作区 | 可折叠上下文面板
────────────────────────────────────────────
Agent Dock + 运行状态栏
```

- 左侧导航只承担模块切换和状态，不重复放模块内筛选。
- 右侧上下文面板是跨模块产物入口：文献引用、图谱邻居、LaTeX 日志、数据产物、复现实验。
- Agent Dock 始终保留当前模块上下文，但默认折叠，避免挤占专业工作区。
- 状态栏统一显示 Git、后端、Tectonic、Python/uv、翻译服务、当前图后端；点击打开健康详情。

### 2. 状态模型先于页面模型

每个模块都必须返回同一种状态：

| 状态 | UI 行为 | 用户行动 |
|---|---|---|
| `ready` | 正常主界面 | 执行核心工作流 |
| `empty` | 说明价值与首个动作 | 创建/导入/连接 |
| `setup_required` | 明确缺失依赖或凭据 | 打开配置或复制命令 |
| `indexing` / `running` | 可取消的进度与阶段日志 | 等待、查看日志、取消 |
| `degraded` | 说明正在使用的降级能力 | 继续使用或完成配置 |
| `error` | 原因、关联 ID、恢复动作 | 重试、查看日志、修复配置 |

禁止只出现“Unknown error”或没有下一步的空白列表。

### 3. 设计令牌与模块语义

保留 OpenCode 主题令牌，不复制原型中的十六进制色值；在 ResearchOS 层定义语义别名：

- 文献：蓝；概念：紫；笔记：橙；代码/实验：绿；数据/图表：青。
- 状态：ready/processing/degraded/error 使用同一套标签、图标和文案。
- 默认主题采用 dark-first 的高密度科研工作台，同时保证现有主题可切换。
- 统一 4px 间距、2/4/6/8px 圆角、发丝边框、Inter 正文与 JetBrains Mono 数据/日志。

### 4. 共享组件必须有清晰边界

不要把每一个模块都改成一个新的“大页面组件”。先提供以下可复用部件；它们只接收真实的项目状态和动作，不拥有业务数据：

| 组件 | 责任 | 不能承担的责任 |
|---|---|---|
| `ResearchWorkspaceShell` | 模块导航、内容宽度、右侧抽屉、底部状态栏 | 模块的查询、写入或运行逻辑 |
| `ModuleState` | 空、配置缺失、运行、降级、失败、成功的统一展示 | 把错误吞掉或把所有失败改成空状态 |
| `DependencyBadge` | 展示服务是否可用、版本/后端和配置入口 | 代替真正的连接测试 |
| `EvidenceDrawer` | 显示来源、证据片段、产物去向和跳转链接 | 生成没有出处的“证据” |
| `OperationFeed` | 当前任务的阶段、日志、取消和重试 | 永久保存所有原始日志 |
| `AgentDock` | 传入当前模块、选中资源和项目路径给对话 | 取代模块主操作 |

这使页面只需要提供 `data`、`state`、`primaryAction`、`secondaryActions` 与可追溯 `operation`；视觉层不再猜测业务是否成功。

## 二、以“研究任务”而非“功能页”组织界面

### 1. 文献 → 图谱 → 写作的证据链

每个文献详情都应有固定的动作区：

```text
导入/解析状态 → 阅读与笔记 → 加入图谱 → 插入引用 → 翻译/导出
```

- 导入和解析显示阶段进度、可恢复错误、原始文件路径。
- “加入图谱”后显示图谱节点、最近关系和跳转入口。
- “插入引用”要求选择 LaTeX 目标文件/位置，并返回可撤销结果。
- 详情页面把引用、推荐、翻译状态放在可切换的次级面板，不使主阅读区拥挤。

### 2. 图谱作为证据浏览器，而非只有画布

图谱页面默认分为“画布 + 证据抽屉 + RAG 结果”：

- 顶栏仅保留类型、关系、时间、来源筛选和布局选择。
- 画布必须显示关系图例、当前图后端、索引状态和节点上限。
- 节点抽屉显示来源文件、引用证据、相邻关系，并可跳回文献或笔记。
- RAG 不伪造答案：显示检索模式、降级状态、证据来源和可复制 context pack。

### 3. 资产中心是“运行环境控制台”

不要把 MCP、Skill、Agent、Rules 做成孤立表格。每个资产行显示：来源、作用域、是否持久化、加载状态、最后错误、可执行动作。

MCP 的完整流为：

```text
选择模板/填写配置 → 保存到项目配置 → 连接测试 → 状态/工具数 → 断开、OAuth、编辑、删除
```

其中“保存”和“连接成功”必须是两个独立的结果，避免用户误以为配置已持久化或服务已经可用。

## 三、按依赖风险排序的实施路线

### 阶段 A：可信状态与壳层

1. 清理乱码；统一所有按钮、toast、空状态和错误文本。
2. 建立模块健康聚合接口与状态页。
3. 实现 `ResearchWorkspaceShell` 的右侧上下文面板、Agent Dock、状态栏。
4. 将现有 Literature、Graph、Assets 先接入统一状态模型。

验收：无论缺少 Tectonic、Python、翻译服务或图后端，用户都能知道原因和下一步。

### 阶段 B：三条高频研究任务

1. 文献导入/解析/引用插入闭环。
2. Build graph/节点证据/Graph RAG 闭环。
3. MCP 配置持久化/连接/OAuth/错误恢复闭环。

验收：每条任务都有端到端浏览器测试，且支持空项目、依赖缺失和一次失败后的恢复。

### 阶段 C：编辑、实验与产物

1. LaTeX：编辑、编译、诊断、预览、引用插入。
2. 数据：CSV、执行、日志、图表、插入论文。
3. 绘图和复现：产物库、日志、对比、导出。

验收：任何产物都能回到来源文件、对应任务和下游引用位置。

### 阶段 D：原型视觉验收

对每页在 1440px 宽度下比较原型与实现，并以截图和交互测试记录差异。移动端不是首期目标，但 1280px 宽度不允许遮挡核心操作。

## 四、验收改为“状态 × 任务”矩阵

页面截图只能发现视觉偏差，不能证明项目可用。每个模块的首个主任务必须同时覆盖以下场景：

| 场景 | 必须验证的结果 |
|---|---|
| 空项目 | 页面说明第一个动作，主按钮可点击，不能显示伪造统计数据 |
| 正常完成 | 成功产物可见、可打开、可在下游模块使用 |
| 依赖缺失 | 显示具体缺失项与配置入口，不能只报网络/未知错误 |
| 可恢复失败 | 保留输入和失败原因；修复后可重试，无需从头录入 |
| 降级运行 | 明示实际使用的后端/检索能力及功能限制 |

验收脚本应从浏览器完成用户动作，再通过 API 或文件系统确认持久化结果；不以“按钮被点击”“toast 出现”作为成功标准。

### 每个模块的首要验收任务

| 模块 | 第一个必须通过的真实任务 | 下游可观察结果 |
|---|---|---|
| 文献 | 导入 PDF，获得可编辑元数据和引文键 | 图谱可发现该文献；LaTeX 可插入引文 |
| 图谱 | 对项目文件 Build graph，查看节点证据 | 能打开来源文件；问答附带证据与后端状态 |
| 资产 | 保存 MCP 后完成连接测试 | 重新进入项目仍存在，显示工具数和连接错误 |
| LaTeX | 编辑并编译一份文稿 | 诊断可定位；PDF/引用插入可见 |
| 数据 | 导入 CSV，运行分析单元 | 日志和图表可回到笔记本来源 |
| 绘图 | 生成并保存一张图 | 可插入论文或导出 |
| 复现 | 发起一次可追踪运行 | 记录命令、环境、日志和产物 |

## 五、避免重新陷入“看起来完成”的机制

1. **先接状态，再加交互。** 新按钮若没有后端动作、持久化位置和失败恢复路径，就不进入页面。
2. **以一个项目数据源为中心。** 路由携带的 workspace、操作 ID、资源 ID 在抽屉、toast、日志和下游跳转中保持一致，避免组件各自读取不同目录。
3. **把能力差异显式化。** SQLite、Neo4j、Memgraph、TuGraph 以及本地/远程 MCP 不共享的能力，必须在状态详情中说明，不能悄悄退化。
4. **每次只交付一个纵向切片。** 例如先完成“PDF 导入到可插入引文”，而不是同时铺开文献列表、阅读器、推荐、翻译的半成品。
5. **视觉调整后回归真实操作。** 每一页变更后运行成功、空、缺依赖、恢复四个浏览器用例；截图仅作为补充证据。

## 六、建议的交付顺序和完成定义

1. 完成壳层与 `ModuleState`，先让已有页面的错误不再失语。
2. 完成文献、图谱、资产三个纵向切片，并给每项在优化清单中打勾。
3. 完成 LaTeX、数据、绘图、复现的真实运行用例；没有本地依赖时必须验证 setup 引导。
4. 最后统一处理间距、密度、主题、动效和 1440px 截图差异。

“完成”只在以下条件同时满足时标记：实现已合入页面、后端真实可用、至少一条浏览器端到端测试通过、缺依赖和错误恢复有明确界面、相关清单已更新。视觉接近原型但无法完成主任务，不能标记完成。

## 七、实施纪律

- 不用“静态 mock 数据”填满界面；未配置的能力应显示 `setup_required`。
- 不为了统一后端而抹平差异；图后端、Python、Tectonic、MCP 都必须公开能力和降级状态。
- 一个页面只保留一个主操作，次级操作进入抽屉、溢出菜单或上下文面板。
- 每完成一个模块，补一条浏览器验收：成功、空状态、依赖缺失、失败恢复。
- 原型是视觉和交互方向，不覆盖真实运行状态与安全边界。
